# Fenix Think

把想法整理成有依据的判断或可执行方案。先明确目标与约束，再推荐实现方向；只做规划时不修改实现。

## 规划规则

- 读取相关项目规则、现有实现和既有决策。配置、默认值和接口以当前文件为准；历史偏好只作线索，涉及历史上下文时读[历史上下文规则](references/durable-context.md)。
- 明确要解决的问题、成功标准、范围和限制。已有材料能确定的选择不重复询问；存在会实质影响成本、行为或权限的未决选择时再提问。
- 优先检查框架内置能力和官方方案；复杂或反复失败的问题，再研究成熟实现。说明哪些机制可复用，不按固定项目数量做调研。
- 给出一个推荐方向及依据。只有取舍可能改变决定时才比较替代方案；判断现有路径或更小改动能否满足目标，不为优雅新增抽象、配置或服务。
- 架构方案按需明确组件职责、数据流、接口、存储和失败处理。图用于解释难以用文字表达的关系，不以文件或组件数量强制绘图。
- 检查支撑方案的关键假设。外部依赖、并发或迁移会影响结果时，说明故障、规模、恢复和回退的取舍，避免为没有证据的风险堆叠防御层。
- 新工具、运行时、依赖和账号是实施成本。说明必要前提，遵守项目限制；能做只读核实时再核实，不把缺少访问或工具写成已验证。
- 将研究结论推广为公共规则时，保留可复用判断，排除其他项目的私有路径、命令和临时状态。

## 按任务处理

- **目标明确的小方案**：简述改哪里、为什么、怎样验证，以及影响决定的风险，不套完整架构模板。
- **价值、可行性、保留或移除判断**：读[价值判断](references/mode-evaluation.md)。
- **一批可独立接受或拒绝的需求**：读[需求分流](references/mode-triage.md)。
- **报错、崩溃或回归**：使用可用的 `fenix-hunt` 或原生诊断能力，先查根因。
- **用户操作、界面或命令交互设计**：使用可用的 `fenix-design` 或原生产品设计能力；纯架构规划留在本技能。

## 交付与实施

交付与任务相称的判断或方案。实施计划应包含具体范围、关键接口与改动位置、依赖、验证方式，以及涉及状态变更时的失败处理。将阻塞实施的未知项查清或明确列为前置条件，不用占位符伪装成已完成决策。

只有分阶段有独立交付价值时才拆阶段。允许将尚不确定的部分设计成有明确问题、产物和退出标准的试验，不把未知实现写成承诺。

只要求规划时交付方案；已授权同一任务的实施且方向已确定时，检查当前状态后继续，不要求重复批准。只在范围扩大、关键选择未决或实际冲突使执行不安全时暂停。方案获认可不自动授权提交、推送或发布。
