# 历史比较与回归

用户提供曾经正常的版本、提交、构建、截图或文件时，把它作为比较依据；先核对实际差异，不从“以前是好的”直接推定某个提交有错。

## 比较与二分

- 先读取工作区状态。先前已知正常且差异较小时，直接比较对应路径；只有回归点未知、范围较大且有可靠的通过／失败判据时才二分。
- 保护暂存、未暂存与未跟踪文件。需要切换历史状态时优先使用临时分离工作树，不在共享工作区执行清理或自动 stash。
- 二分前定义非交互测试命令，确认它能区分正常与故障版本；环境或依赖导致无法判断的提交不能标为产品失败。
- 用 Git 记录 `git bisect good`／`bad`。找到候选提交后读实际差异并验证因果，不把二分结果直接当根因；完成后先 `git bisect reset`，再移除自己创建的临时工作树。

## 截图与重复故障

列出当前结果与参考结果的具体差异，为相关症状指定可检查的预期。保留用户描述的入口、冷启动、模式切换与时序条件；从应用内部打开正常，不代表文件关联或深链入口正常。

渲染、状态、字体管线和时序回归按故障诊断处理，主观风格偏好才交给设计。对共享组件或同类拒绝分支检查相关位置；不要把参数反复调整无效直接等同于必须重构，先验证约束和数据路径。

## 回归保护

在隔离环境对照旧故障与修复，保留能区分二者的测试或复现材料。检查断言失败能否让测试失败，以及空结果、跳过或错误字符串是否可能让测试假通过；负向断言需要有效的故障对照，不机械要求特定测试写法。

无法恢复旧环境或复现间歇故障时，交代已取得的证据与未验证环节，提供具体检查步骤，不声称完成了未运行的前后对照。
