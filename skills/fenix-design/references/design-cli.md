# CLI 与 Agent 调用

先明确直接使用者是终端用户、脚本、AI Agent，还是多者共用；从共同任务设计能力，再区分呈现方式。已有命令的名称、输出和默认行为可能被脚本依赖，先读实际帮助、实现与调用方。

## 命令与交互

- 用用户任务组织命令，不把内部模块或 API 路径直接当作产品结构。单一操作保持简单；多步骤操作只有在判断已确定、失败和恢复语义清楚时才封装成一个命令，保留需要使用者决定的分支。
- 给每个命令明确输入、默认值、结果、影响范围和失败条件。用户应能从帮助、参数说明和必要示例发现能力，不必先读源码。区分设计中的命令与已经可执行的命令。
- 为人提供可扫读的帮助、结果和可行动的错误信息。脚本和 Agent 应能通过参数完成任务；关闭 stdin、管道输出或无人值守时，不等待交互输入，不自动翻页或输出动画。
- 主结果与诊断分开。结构化输出保持可解析，进度和诊断不混入结果流；明确错误通过哪个流、字段和退出码表达。成功、空结果、部分完成、输入错误和执行失败的语义需一致，沿用产品已有约定。
- 只返回当前决策需要的信息，同时保留查询详情和诊断的路径。对列表、分页、截断和长任务，说明覆盖范围与是否完成；不把截断后的结果当作全量，不将超时等同于操作未发生。
- 涉及配置或认证时，明确参数、环境和配置文件的优先级，以及当前环境与权限。不要把凭据放进命令示例、可见输出或日志；不为原型连接真实账号。
- 对写入和批量操作，给出可检查的对象和影响；需要预览时让预览真正只读。重试前能辨认已完成部分；按任务设计幂等、状态查询或恢复机制，不默认自动重复写入。

## Skill＋CLI

- Skill 解释何时使用、如何选择操作及必要的业务判断；CLI 执行确定性步骤并提供当前接口事实。避免在 Skill 中复制整份命令手册，按需读取帮助或随版本维护的接口资料。
- 从自然语言请求推演能力发现、输入补全、命令选择、结果解释和下一步动作。检查同一对象的名称、标识和状态在 Skill 与 CLI 中是否一致。
- 核实目标 Agent 能执行哪些工具、怎样发现 Skill、从哪里读取命令契约。写明缺失的运行前提；不把存在 `SKILL.md`、工具自称成功或版本字符串相同当作实际加载与兼容的证据。
- Skill 指令、帮助和已安装 CLI 应描述同一能力；改名或移除接口时检查已有调用。按项目实际版本来源维护，不新增相互竞争的版本字段，也不把正式发布流程强加给原型。

## 验证

用真实命令覆盖这次设计改变的成功与失败分支。检查非交互执行、结果解析、退出码和实际状态；必要时检查取消、超时后查询、重复调用和部分完成。终端排版改变后读取实际输出，视觉细节按 UI 资料处理。

Agent 试用时从新的上下文给出任务和材料，观察它是否能发现正确入口、构造有效参数、解释结果并在边界处停止。测试能力发现时不要提前告诉它选哪个技能或执行哪条命令；只测试执行时可以明确入口。保留原始调用与结果用于分析，不要求唯一固定的调用顺序，也不凭主观感觉声称节省了时间或 token。
