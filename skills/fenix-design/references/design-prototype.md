# 原型与验证

原型用于检验会影响设计选择的不确定性。先写明要回答的问题、已有证据和什么观察会改变当前方案，选择少量真实任务描述成功结果，再决定原型形式。

- 按用户请求交付：方案用流程和交互示例表达；要试用时做最小可运行原型；要实现时再满足正式交付要求。不因进入原型流程就修改已有产品或执行发布。
- 用用户会说的话描述任务，覆盖主要路径和相关边界；指定可检查的结果，避免把预期答案直接教给试用者。不为追求场景数量补造需求。
- UI 可以用线框、交互页面或局部组件；CLI 可以用命令脚本和状态数据；复杂流程可以用可视化演示辅助理解。按待验证的问题选择，不强制 HTML、TUI 或某种框架。
- 复用现有环境，提供实际验证过的启动入口。使用隔离目录、模拟数据或明确的测试服务，展示相关状态与影响。标明哪些是模拟、哪些已接通真实能力；模拟应覆盖有意义的分支，而非所有输入返回同一成功结果。
- 把精力放在待验证的交互和状态，少做无关装饰与基础设施。错误、等待、取消或恢复若是设计问题的一部分，就实现并试用这些路径，不能以原型为由省略。
- 记录试用中的实际选择、误解、停顿、失败和最终状态，区分观察与推断。修改造成问题的设计，再用相近任务复查；不要为了让原型通过而放宽成功标准。

对 Skill＋CLI，分别检查能力发现与执行；允许时在相同模型、工具和输入条件下比较有／无 Skill 或前后版本，并说明次数与局限。人工走通、脚本测试、Agent 试用和真实用户试用分别记录，不相互冒充；没有可用 Agent 运行环境时保留场景与检查方法，明确尚未试用。

交付原型、运行方式和问题的结论，列出已验证、待验证及值得继续投入的部分。关键假设仍不成立时说明原因和下一步，不把演示效果称为产品验收；不自动删除原型、建分支、提交或对外发布。
