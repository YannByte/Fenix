# Fenix Design

从用户要完成的事情出发，设计入口、操作、反馈和结果，再选择合适的界面与实现方式。按任务交付设计方案、可试用原型、实现或审阅意见。

## 设计规则

- 先读现有产品、用户材料、使用记录和项目约定，明确谁使用、在什么情境下、想完成什么、怎样算成功。区分直接操作的人、代人操作的 Agent 和审批等相关角色；不要编造用户研究或需求证据。
- 从已知材料判断使用频率、经验、设备、可访问性和权限约束。只询问会改变方案的缺口；可暂定的内容标为假设，不把没有回复当作授权。
- 围绕主要任务组织信息与能力，沿用用户理解的名称。写清用户从哪里进入、需要做哪些选择、如何知道当前状态、怎样确认完成；已有产品优先复用成熟交互，不为统一风格重做整个产品。
- 按实际流程考虑等待、空结果、输入错误、权限不足、部分完成和取消恢复。区分尚未完成与确实没有结果，保留用户输入和已完成工作；每一步都应让使用者知道还能做什么。
- 明确动作影响的对象、范围和可恢复性。预览不得产生真实变更，取消应停止后续操作；涉及并发、重试或长任务时，设计如何查状态、避免重复执行和恢复工作，按实际风险决定确认方式。
- 按不确定性选择交付物。流程或命令示例足以讨论时先用它；需要观察操作和状态时做最小可运行原型；视觉有争议时再比较可感知的方案。不默认把所有原型做成网页或完整产品。
- 只审阅或设计时不改实现；已要求制作原型或实现时，在授权范围内完成并验证。不要把视觉方向、设计方案或模拟成功当作业务能力已经可用。

按涉及的产品界面选择资料；跨 UI、CLI 的同一任务沿用相同对象、状态和结果语义。原型验证可与任一种界面结合。

## 验证与交付

沿核心任务走一遍入口、关键选择、等待、结果和恢复，按此次改动验证相关边界。UI 查看真实渲染和目标设备上的操作；CLI 运行真实命令并检查输出、退出状态和实际副作用；Agent 场景观察它如何发现、选择和调用能力。

用结果文件、状态或环境变化确认完成，不只看演示截图和 Agent 自述。报告具体观察、影响决策的假设及未验证部分；没有真实用户或 Agent 试用时明确说明。按请求返回成果，不固定附加评分表、设计文档或长篇报告。
