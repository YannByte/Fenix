# 交付流程

用于判断是否值得发版，或执行已授权的提交、推送、发布与公开跟进。沿用[技能入口](../SKILL.md)的审阅、工作区保护和证据要求；交付流程不自动扩大授权。

## 选择交付面

- **仅判断是否发版**：从实际渠道上一版本对应源码比较变更，说明用户价值、兼容性、主要风险和版本建议。结论不授权实际发布。
- **提交／推送**：检查目标差异、相关验证和必须同步的跟踪资源；不额外要求 Tag、发版记录、注册表或发行资产。
- **打包／发布**：读取项目分发约定，按[项目上下文](project-context.md)核对版本、生成物、包内容、安装和实际发布渠道。
- **回复／关闭／合并**：仅执行用户已授权的操作，使用[公开回复流程](public-reply.md)核对身份、内容、读回和关闭条件。

同一任务已授权的审阅、修复、验证、提交和推送应连续完成。中途状态询问不撤销原授权；新增动作或未覆盖风险才需要另行确认。没有目标改动时不创建空提交。

## 提交与推送

核对当前 HEAD、分支、远端、暂存与未暂存内容，只暂存本次目标路径。保留其他修改和部分暂存；Git 写操作顺序执行，避免并发改变索引。

提交前以及推送前重新核对 HEAD 与目标。出现不明提交或影响本次动作的并发变化时先查清，不自动重置、变基或改写历史。按项目约定记录验证与回退方式，不自动升级版本。

只执行已有授权的远端动作。用户指定账号时先核对实际认证身份，不能静默替换。普通推送后读取目标远端提交与相关 CI；本地提交、远端源码、CI 和已分发版本分别说明。

## 打包与发布

读取公开文档、清单、CI 和发布入口，明确预览、测试或稳定渠道。核对各处版本与唯一来源，以及生成物、包清单、新增资源、执行权限和可选依赖；不要把源码测试通过当作包内行为通过。

发布文案可用 `fenix-write` 或原生写作能力，沿用项目已有语言和标题约定，按实际用户变化决定条目数量。内部重构不自动写成用户功能，计划和未分发的改动不能写成已上线。

能预览时先检查打包或发布预览。按项目要求验证签名、校验信息、安装与运行行为；缺少必需证据就报告具体阻塞。发布后读回实际资产或注册表状态，不仅检查网页文字、文件大小或工作流颜色。

一组改动可能同时包含打包后才生效的客户端与推送后自动部署的服务，分别核对状态。预览渠道不代表稳定发布，也不授权改动稳定渠道。

候选版本被取消、反复返工或延迟后重新放行时，读[发行面检查](release-surfaces.md)中对应部分，重新核对实际基线与未解决风险，不沿用失效的通过结论。

## 公开跟进与异常

回复或关闭前重读具体 Issue／PR，确认目标、当前状态和用户能取得的版本。提交／推送授权本身不授权评论、关闭、合并或添加表情；只做用户明确要求的跟进，并读回核对。

贡献者分支修复需要核对修改权限、远端、分支和当前提交，保留贡献者工作。方向接受但证据不足时继续保留待处理状态，不把无法复现直接等同于无效。

网络或 API 失败后先查询最终状态。发布、Tag、发行创建等可能已成功的写入，验证超时代表未知，不能直接重复执行。按项目有界策略做只读检查；仍无法确认时报告精确未知状态。

交付时只列相关状态与证据。每项已授权工作明确为完成、无需执行或受阻，不能用一次成功推送替代未完成的本地提交，也不能用源码更新替代实际分发。
